# UI languages (English / 한국어)

The console (web, desktop app, Android app), the server's login page and the desktop app's own pages and menus
speak English or Korean. The user picks it in **Settings → Language**; it applies at once (no reload).

## Where the choice lives

| Where | What | Who reads it |
|---|---|---|
| `localStorage.hrh_lang` | `en` / `ko` | this browser / app, instantly at start (also the desktop app's Mate windows, which follow live through the `storage` event) |
| `GET/PUT /api/preferences` → `{language}` (`app_kv['ui_preferences']`) | the account's choice | every device: the console applies it after loading, so another device follows |
| cookie `hrh_lang` (1 year, `SameSite=Lax`) | the same | the server-rendered login page (`/login`), before anyone is signed in |
| desktop `settings.json` → `language` (set through `hrhNative.setLanguage`) | the same | the tray / app menu, notifications, the action bar, the local connect and retry pages |

Without a choice the browser's language decides (Korean if it is listed before English, else English); the login
page uses `?lang=` → the cookie → the stored preference → `Accept-Language`.

Mate replies and personas are separate: a mate's reply language is the mate's own setting and is not changed by
the UI language.

## Code

`frontend/src/i18n/`:

- `index.ts` — the store (`useI18n`), `useT()` (a component re-renders when the language changes), `tr()` for code
  outside React (stores, notifications), `t.rich()` for messages with markup.
- `en/<namespace>.ts` — the English messages; their keys are the `MsgKey` type, so `t("nav.newChat")` is checked.
- `ko/<namespace>.ts` — typed against en (`Messages<"nav">`): a missing or extra key does not compile.
- `format.ts` — `fmtNum`, `fmtDate`, `fmtTime`, `fmtDateTime`, `relTime`, `fmtDuration` in the UI's locale.

Messages:

- `{name}` is filled from the vars: `t("nav.updateAvailable", { latest, current })`. Numbers are formatted for the
  locale (`1,234`) — pass years, ports and ids as strings.
- Plurals: `{ one: "{count} file", other: "{count} files" }`, chosen by `count` (or the first number). Korean
  usually needs only a string.
- Markup: `t.rich("nav.defaultPasswordWhere", { b: (s) => <b>{s}</b> })` — `<b>…</b>` calls `b`, `{x}` puts a node.
- Only the active language's catalog is downloaded (a lazy chunk); `main.tsx` waits for it before the first render.

Checks: `npm run test:i18n` (in `frontend/`) runs `test/i18n.test.ts` — ko has exactly the en keys, the same
`{placeholders}` and `<tags>`, no empty message, and every key is used somewhere in `src/` — and
`scripts/i18n-scan.mjs`, which lists JSX text, `title` / `placeholder` / `aria-label` and similar literals still in
English in translated files.

## Korean style

- Sentences in 해요체: "서버에 연결할 수 없어요.", "다시 시도해 주세요." Never 합니다체 mixed in.
- Buttons and labels as short nouns / verb stems: 저장, 취소, 다시 시도, 지금 바꾸기, 새 채팅.
- Tooltips: a short phrase, no final period unless it is a sentence.
- Keep product, model and engine names, code, paths, file types, keyboard keys and units as they are: My Mate Geny,
  Claude Code, Codex, Claude, Opus 5.5, GPT-6.1, Live2D, API, CLI, MCP, Git, GitHub, `.deb`, Ctrl, MB/s.
- No spaces lost around Latin words: "Claude Code 세션", "API 키".

## Left in English on purpose

Text that comes from the server or a tool as is (error details, log entries, git output, MCP server states), product,
model and engine names, paths and file names, git status letters, and the dev-only Avatar Lab. Electron's built-in
menu roles (Edit, Window, Reload…) use Electron's own labels.
